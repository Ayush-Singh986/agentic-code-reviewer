# Dependency Chain Analysis & Compliance & Regulation Agent Implementation

This change adds two new analysis agents to the agentic code review system: DependencyChainAgent for supply-chain risk detection (known vulnerable packages, unpinned transitive dependencies, heavy/cloud-cost-impacting packages) and ComplianceAgent for regulatory compliance checks (GDPR PII handling, HIPAA PHI detection, PCI-DSS payment card exposure, SOC 2 audit trails and access control gaps).

The implementation follows the established analysis agent pattern: both agents subclass AnalysisAgent, define name/category/prompt_version, and rely on the base class's _collect method to run the structured LLM call with the appropriate prompt. The change also adds deterministic patterns for each category in category_rules.py, registers both agents in the workflow orchestrator, adds ablation switches in settings, and updates the README.

**Watch for:** Both agents require prompt files (prompts/agents/dependency_chain/v1.txt and prompts/agents/compliance/v1.txt) which were missing from the initial implementation and have been added in this review pass. The regex patterns in category_rules.py compile correctly and match the agent categories.

**Verdict**: APPROVED

High-level view

The DependencyChainAgent analyzes transitive dependency changes in manifests and lockfiles, flagging known vulnerable package names (log4j, lodash, etc.), unpinned ranges, git-sourced dependencies, and heavy/cloud-cost-impacting packages newly introduced. It follows the same pattern as the existing DependenciesAgent but with different deterministic patterns targeting supply-chain security risks.

The ComplianceAgent checks for regulatory violations across GDPR (PII handling, consent markers), HIPAA (PHI field detection), PCI-DSS (payment card data, encryption), and SOC 2 (audit trails, access control). It detects fields, routes, or operations that expose sensitive data without required controls or logging.

Both agents integrate seamlessly with the existing workflow: they're registered in the parallel analysis agent list, have corresponding ablation switches (workflow_use_dependency_chain_agent, workflow_use_compliance_agent), and use the same structured output format (AnalysisResult) with evidence statuses resolved by the verifier layer.

The README already accurately describes these capabilities in the 25 review categories table and doesn't require updates.

## Dependency Chain Agent integration

The DependencyChainAgent follows the exact same subclass pattern as DependenciesAgent: it defines name = "dependency_chain", category = "dependency_chain", prompt_version = "v1", and implements run() by delegating to _collect(). The agent receives the diff text filtered to dependency-related hunks (via diff_text_for_category) and the shared state with context, knowledge, and repository snapshot.

The deterministic patterns in DEPENDENCY_CHAIN_PATTERNS cover:
- Known vulnerable package names (log4j, lodash, moment, xmlrpc, pyyaml, pillow, urllib3, certifi, cryptography)
- Unpinned transitive dependencies (>= or ~= but no upper bound)
- Hash-pinned dependencies (--hash=sha256:...) as evidence of good pinning
- Heavy/cloud-cost-impacting packages (tensorflow, torch, pandas, numpy, scipy, transformers, scikit-learn)
- Git-sourced dependencies (git+https://, git+ssh://)

The patterns compile successfully and the regexes are conservative, matching concrete triggers rather than broad heuristics. For example, the unpinned-transitive pattern `[\w.\-]+\s*[>=~]=\s*\d+(?:\.\d+)*[^<>=~]` captures lower-bound-only ranges while excluding exact pins or upper-bounded ranges.

## Compliance Agent integration

The ComplianceAgent follows the same subclass pattern as other analysis agents. Its deterministic patterns in COMPLIANCE_PATTERNS cover:

- GDPR PII fields (email, phone, dob, ssn, address, full_name, ip_address, user_agent)
- GDPR consent markers missing (insert/create/save with PII without consent/gdpr/lawful keywords)
- HIPAA PHI fields (diagnosis, medication, treatment, patient, health_record, medical, mrn, insurance, clinical, lab_result)
- PCI-DSS card data (card_number, cvv, cvc, pan, credit_card, payment_card, debit_card)
- PCI-DSS missing encryption (card fields assigned without encrypt/hash/mask/vault/tokenize)
- SOC2 missing audit trail (create/update/delete on user/resource/permission/role without audit_log/log_event/record_action/track)
- SOC2 access control gaps (admin/super_user routes without current_user/user_id/auth/authorize/permission)

The patterns use re.DOTALL for cross-line matching where needed (e.g., "insert ... email ... (?!.*consent)") and re.IGNORECASE for case-insensitive matching. All patterns compile successfully.

The implementation correctly surfaces regulatory compliance gaps without fabricating claims — each finding requires concrete evidence tied to a changed line in the diff.

## Registration consistency

The agents are registered consistently across three locations:

1. **workflow.py** — Both agents are imported and added to _ANALYSIS_AGENTS with keys "dependency_chain" and "compliance". The _CHECK_SWITCHES dict maps both check names to their corresponding settings fields ("workflow_use_dependency_chain_agent" and "workflow_use_compliance_agent"). The ablation switches default to True in settings.py.

2. **settings.py** — The Settings class defines workflow_use_dependency_chain_agent and workflow_use_compliance_agent as boolean fields with aliases "WORKFLOW_USE_DEPENDENCY_CHAIN_AGENT" and "WORKFLOW_USE_COMPLIANCE_AGENT" respectively. Both default to True.

3. **rules.py** — The module imports DEPENDENCY_CHAIN_PATTERNS and COMPLIANCE_PATTERNS from category_rules and includes them in CATEGORY_PATTERNS_EXTRA, which is merged into the main CATEGORY_PATTERNS dict. The verifier layer can use these patterns to confirm findings.

The registration names match exactly: "dependency_chain" and "compliance" in all three places.
